# Производительность — чеклист

Живой список узких мест. Идём сверху вниз: обсуждаем → решаем → отмечаем.

Пороги LOD (для контекста): `cellPx = BASE_CELL * scale` (`BASE_CELL = 8`).

| Слой | Условие | `scale` (примерно) |
| --- | --- | --- |
| Крестики «готово» | `cellPx >= 12` | `≥ 1.5` |
| Zoom-wash (старт → max) | с `cellPx >= 12` до `100` | `1.5…12.5` (alpha 0→max) |
| Мелкая сетка клеток | `cellPx >= 24` | `≥ 3` (как символы) |
| Символы / иконки | `cellPx >= 24` | `≥ 3` |
| Макс. зум | `cellPx = 100` | `= 12.5` |

## Чеклист

### 1. [x] Символы/иконки на каждом кадре pan/zoom (сделали A)

**Проблема:** при `cellPx >= 24` для каждой видимой клетки на кадр: `threadAt` → (часто) `tinycolor` / `blendOver` / `contrastInk` → `fillText`. Viewport уже учитывается; узкое место — стоимость **на клетку × на кадр**. На среднем/сильном зуме на слабых устройствах (iPhone 7) это главный тормоз жестов.

#### Идея A — кэш цвета ink / ключ `paletteIndex + wash`

Сейчас на каждую клетку заново: парсинг цвета, blend с wash, luma, выбор чёрный/белый.

**Суть:** кэшировать результат. Ключ, например, `paletteIndex` + квантованный alpha wash (или строка `washColor` + ступень зума). Значение — `'#000'` / `'#fff'`.  
157 ниток × немного ступеней wash ≈ крошечная таблица. `fillText` остаётся, но без `tinycolor` на каждую клетку.

- Плюсы: мало кода, заметный выигрыш CPU, логика рисования та же.
- Минусы: сам `fillText` всё ещё дорогой на тысячах клеток за кадр.
- Сложность: низкая.

#### Идея B — реже перерисовывать символы / отдельный слой

Сейчас pan/zoom → полный `draw()` → снова все видимые символы.

**Варианты:**
1. **Throttle символов** — заливка/wash/сетка на каждом кадре; символы раз в N мс или только после конца жеста (`pointerup` / debounce).
2. **Отдельный canvas символов** — нижний слой (цвет) двигается с pan/zoom дёшево (`drawImage`); слой символов пересобирается только когда сменился набор видимых клеток / scale / wash, не на каждый пиксель pan.

- Плюсы: жест становится гладким; символы «догоняют».
- Минусы: throttle → краткая «пустота» или плавание символов; второй canvas — больше состояния и синхронизации.
- Сложность: средняя / выше средней.

#### Идея C — атлас глифов вместо `fillText`

`fillText` + смена `font` на клетку тяжелы для CPU/GPU.

**Суть:** один раз (или при смене размера) нарисовать каждый нужный символ/FA-глиф в спрайт (чёрный и белый вариант). В кадре — `drawImage` куска атласа в клетку. `drawImage` обычно дешевле текста.

- Плюсы: лучший потолок FPS при большом числе видимых символов.
- Минусы: генерация атласа, DPR/scale (несколько размеров или scale атласа), память, сложнее поддержка.
- Сложность: высокая.

**Практичный порядок:** A → при необходимости B → C если всё ещё мало на целевых телефонах.

**Решение:** сделали **A** — `getInkTable(wash)`: таблица ink на всю палитру кэшируется, пока строка wash не меняется; в кадре на клетку только lookup + `fillText` (без `tinycolor`/`blendOver`). `fillText` по-прежнему на каждую видимую клетку — при необходимости дальше B/C.

### 2. [x] Сброс `canvas.width` / `canvas.height` в каждом `draw()`

**Проблема:** даже если CSS-размер и DPR не менялись, присвоение `width`/`height` пересоздаёт буфер и чистит canvas — лишняя работа на каждый pan/zoom.

**Идеи:** ресайзить только когда изменились `cssW`, `cssH` или `dpr`.

**Решение:** сделано — буфер и `style` обновляются только при смене `cssW` / `cssH` / `dpr` (или рассинхроне `canvas.width/height`); каждый кадр по-прежнему `clearRect` + отрисовка.

---

### 3. [x] Обводка активного кода — много `strokeRect` (сделали A)

**Проблема:** при выбранном `activeCode` по всем **видимым** клеткам этого кода: отдельный `strokeRect` (+ `save`/`restore`). Частый цвет (например фон) → сотни обводок на кадр pan/zoom. Рамки навигатора/компаса — единицы, они не в фокусе этой проблемы.

> Уточнение: у `activeCode` обводка **всегда solid** (`dashed: false`). Пунктир только у первой клетки навигатора/компаса. В общем `drawCellFrames` оба типа рамок; батч по стилю (цвет + dashed + ring) как раз отделяет сотни solid activeCode от единиц с пунктиром.

#### Идея A — батчить в один path

Сейчас: N раз `strokeRect` ≈ N отдельных stroke.

**Суть:** для всех рамок одного стиля (один цвет, один dashed, один ring) собрать `rect` в **один** `beginPath` и сделать **один** `stroke()`. Для activeCode это почти всегда одна группа: solid + один цвет + ring 0.

- Плюсы: меньше вызовов GPU/state; код локальный в `drawCellFrames`.
- Минусы: группы по стилю (nested rings / разные цвета) — несколько stroke, не один на весь мир.
- Сложность: низкая–средняя.
- Влияние на UX: нет.

#### Идея B — оффскрин-слой рамок

**Суть:** когда меняются `activeCode` / цвет рамки / scale (толщина линии), один раз нарисовать все рамки активного кода на отдельный canvas (или пересобрать path). На pan — `drawImage` этого слоя вместе со схемой (с тем же pan/scale), без N `strokeRect` каждый кадр.

Нюанс: при pan меняется **набор видимых** клеток → слой надо либо строить на всю схему (память), либо инвалидировать при смене visible range (тогда выигрыш только внутри «стабильного» кадра жеста — слабее).

- Плюсы: pan может стать дешевле, если слой на всю схему или кэш умный.
- Минусы: память, инвалидация, синхрон с zoom (lineWidth зависит от scale).
- Сложность: средняя–высокая.
- Влияние на UX: нет, если инвалидация корректная.

#### Идея C — LOD / упрощение на малом зуме

**Суть:** не рисовать поклеточные рамки, пока клетка мелкая. Например:
- при `cellPx < N` — не обводить каждую клетку, а только подсветить swatch в палитре / dim остальных;
- или рисовать разреженную обводку / полупрозрачный overlay по bounding-box кластеров;
- или включать поклеточные рамки только с того же порога, что символы (`>= 24`).

- Плюсы: резко режет работу там, где рамок больше всего (много клеток на экране).
- Минусы: меняется UX — на среднем зуме «красной сетки» по цвету может не быть или она другая.
- Сложность: низкая (порог) … средняя (кластеры).
- Влияние на UX: **да**, осознанный продуктовый выбор.

**Практичный порядок:** A (без смены UX) → при нужде C (если ок упростить UX) → B если всё ещё мало.

**Решение:** сделали **A** (батч rect), затем уточнили UX/perf для activeCode:

- **ActiveCode** — не поклеточные rect, а **периметр островов** + заливка акцентом @ 25% (`drawCellIslandFrames` / `drawActiveCodeHighlight`): в path только внешние рёбра, один `stroke`.
- **Nav/compass** — по-прежнему единицы rect в `drawCellFrames` (батч + tint 25%); ring учитывает периметр active на той же клетке.
- Толщина всех акцентов — `accentStrokeWidth()` (общие константы).

Идеи B/C выше по-прежнему в запасе, если периметра мало на огромных active-регионах.

### 4. [x] Мелкая сетка — много линий (сделали B)

**Проблема:** при достаточном зуме строится path разлиновки клеток (не блок-сетка 10×10). Раньше path на **всю** схему при `cellPx >= 10`; сейчас порог как у символов (`>= 24`) + идея B. Цвет — `cellDividerColor` в сторе («Цвет разделения»).

#### Идея A — оставить как есть

Пока не трогаем: один path, ~400 линий, один stroke. Имеет смысл, если после пунктов 1–3 pan/zoom уже ок на целевых устройствах.

- Плюсы: ноль риска, ноль кода.
- Минусы: работа на каждый кадр даже вне viewport.
- Влияние на UX: нет.

#### Идея B — только visible range

Как у символов: строить вертикали/горизонтали лишь в пределах `visibleCellRange`, а не `0…width` / `0…height`. Отрезки тоже обрезаны по видимому прямоугольнику.

- Плюсы: на сильном зуме линий мало; код локальный рядом с текущим `showGrid`.
- Минусы: на каждом кадре пересчёт диапазона (дешёвый); при pan набор линий меняется — без кэша path.
- Сложность: низкая.
- Влияние на UX: нет (те же линии, просто не рисуем за экраном).

#### Идея C — кэш сетки в оффскрин

Пока не менялись `scale` / размер схемы / цвет линии — один раз нарисовать сетку на offscreen canvas; в кадре `drawImage` с pan/scale. Инвалидация при zoom.

- Плюсы: pan без пересборки сотен `moveTo`/`lineTo`.
- Минусы: память, синхрон с DPR/scale, чуть больше состояния.
- Сложность: средняя.
- Влияние на UX: нет.

**Практичный порядок:** A (если FPS ок) → B (дешёвый выигрыш) → C если pan всё ещё тяжёлый из‑за сетки.

**Решение:** сделали **B** — мелкая сетка по `visibleCellRange` (линии `x0…x1+1`, `y0…y1+1`, длина сегментов только по видимому прямоугольнику). Порог показа: `cellPx >= 24` (как символы/иконки). Блок-сетка 10×10 не трогали. Если всё ещё тяжело — смотреть C.

## Вне скоупа (сейчас ок)

- `colorCanvas` одним `drawImage` — хорошо.
- Zoom-wash одним `fillRect` — хорошо.
- `scheduleDraw` через rAF — хорошо.
- Компактный шаблон схемы (palette + индексы cells) — хорошо.
- Стор / `doneCountByColor` — дёшево относительно canvas.
- Done-метки (veil + крест) только при `cellPx >= 12`; ниже порога не рисуем — на полном отзуме pan не платит за десятки тысяч `fillRect` по `done`.

---

## Заметки (не в чеклисте)

- Поклеточная вуаль done на всём viewport при большом `% done` дорогая даже без крестов (тысячи `fillRect` / кадр). Если снова понадобится done на дальнем зуме — batch path, invert при высокой плотности или bake в слой/colorCanvas, не N×`fillRect` каждый pan.
